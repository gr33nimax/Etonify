# HydraBox 2.0 — UI/Product analysis

Дата: 2026-09-01
Статус: анализ и планирование. Изменений Android-кода в рамках этого документа нет.

## Границы анализа

Backend/runtime считается рабочим: туннель, импорт, построение конфигурации и libbox не являются предметом редизайна. UI должен показывать только понятные человеку результаты этих систем, а не их внутреннее устройство.

Источники: текущие Compose-экраны и product projection в `ui/` и `core/projection/`; историческая карта HB1 в `docs/HYDRABOX2_HB1_PARITY.md`; прежнее UX-ревью `docs/HYDRABOX2_UX_REVIEW.md`; актуальные рекомендации Material 3 Expressive и Android adaptive UI. HB1 использован как каталог возможностей, не как макет для переноса.

## 1. Текущее состояние

### Навигация и экраны

Сейчас есть три верхнеуровневых destination: **Дом**, **Серверы**, **Настройки**. На compact-ширине это bottom navigation, на medium/expanded — rail. Детальные экраны открываются поверх вручную управляемого стека:

| Откуда | Экран | Реальная задача пользователя |
|---|---|---|
| Дом | Трафик | Посмотреть скорость, объём и соединения |
| Дом / Серверы | Источники | Добавить, обновить, переименовать или удалить подписку |
| Настройки | Приложения | Настроить split tunneling |
| Настройки | Внешний вид | Тема и язык |
| Настройки | Диагностика | Логи, детали runtime, экспорт |
| Настройки | О приложении / документы | Версия и legal |

Первый запуск — отдельный блокирующий поток: приветствие → согласие с документами → добавление подписки; его можно временно пропустить. Основная пользовательская модель уже отделена от runtime: `Connection` представляет `NeedsSubscription`, `NeedsServers`, `Idle`, `Connecting`, `Connected`, `Reconnecting`, `Disconnecting`, `Stopped`; `Trouble` сворачивает технические ошибки в шесть объяснимых причин.

### Компоненты и сильные стороны

- В приложении есть единая Material 3 тема, dynamic color на Android и fallback brand palette, светлая и тёмная схема.
- Контрол подключения — заметный отдельный объект, использующий цвет, форму и движение, а не только текст.
- Технические поля (`runtimeState`, `transport`, error code) локализованы в Diagnostics; на Home они не выводятся.
- Есть состояния пустого экрана, подтверждение удаления подписки, поле поиска серверов и приложений, состояния загрузки источника/списка серверов, snackbar для transient-notice.
- Настройки уже разделены на базовые и advanced; у части параметров есть объяснение необходимости переподключения.

### UX-проблемы

1. **Дом не является центром сценария.** Пользователь нажимает большой контрол, но выбор сервера, состояние подписки и результаты последнего сбоя разнесены по разным местам. При ошибке действие может увести на вкладку серверов без контекста причины.
2. **«Серверы» и «Источники» разделяют одну задачу.** Пользователь мыслит: «куда подключиться и откуда взялся этот список». Сейчас управление источником — скрытый detail screen, а список серверов — отдельная вкладка. Это добавляет переходы при первом запуске, обновлении просроченной подписки и поиске сервера.
3. **Первый запуск перегружен legal-этапом и длинным вводом.** Он честно блокирует подключение до источника, но не объясняет, что получится после вставки ссылки, и действие «Позже» ведёт к другому пустому состоянию без продолжения того же контекста.
4. **Переключение сервера недостаточно явно связано с текущим подключением.** Выбор строки меняет настройку и, вероятно, инициирует нужный backend-переход, но интерфейс не даёт понятного подтверждения «переключаемся на …» и не удерживает пользователя в результате операции.
5. **Ошибки местами теряют контекст.** `Trouble` хорош как продуктовая классификация, но Home показывает статус и вторичное действие отдельно; причина, затронутый сервер/источник и прогноз следующего шага не собраны в единую recovery-сцену.
   Есть и конкретные расхождения action contract: secondary action для `CHOOSE_SERVER` вызывает retry вместо перехода к выбору сервера, а `REFRESH_SOURCE` в общем обработчике Home также уходит в retry. Это не вопрос оформления: recovery может выполнить неверное действие.
6. **Настройки смешивают частоту использования.** «Уведомления», «Приложения», anti-leak и ad blocking видны сразу, хотя ежедневному VPN-пользователю обычно нужны только приложения и несколько параметров подключения. Диагностика находится на том же уровне, что оформление.
7. **Приложения — отдельный режим без предварительного объяснения последствий.** Термины «обход выбранных» и «только выбранные» требуют выбора до показа списка; не видно краткого правила, которое сейчас будет применяться.
8. **Трафик — отдельный экран при наличии лишь вторичной ценности.** Для обычного пользователя достаточно компактного connected-summary; подробности нужны по запросу и не должны конкурировать с подключением.
9. **Результаты операций неполны.** У добавления/обновления подписки должны быть отдельные success, failure, empty и partial-success состояния; очищать введённую ссылку до подтверждённого успеха нельзя.

### Проблемы визуального языка

- Выразительный контрол подключения существует изолированно: окружающий Home — вертикальный набор строк и metric tiles, без иерархии «состояние → выбранный маршрут → дополнительная информация».
- Тональные поверхности, форма и motion заданы, но не образуют устойчивую систему ролей: статусы, группы настроек, выбранный сервер и destructive action визуально не имеют единого семантического уровня.
- Текущая навигационная оболочка адаптирует только chrome (bar/rail). Контент на wide window остаётся одноколоночным и растянутым; detail screen не превращается в supporting/list-detail pane.
- Нет чёткой визуальной границы между «важно для подключения» и «информационно». Например, source problem обозначается warning strip, но не становится частью доступного для действия статуса Home.

### Доступность

- Плюс: у connection control есть `contentDescription` и `stateDescription`; статусная группа объявлена polite live region; есть подписи у bottom/rail navigation и back action.
- Риск: иконки в строках и навигации часто намеренно имеют `contentDescription = null`; это корректно только если вся интерактивная строка имеет объединённую семантику. Это нужно проверить семантическими тестами и TalkBack.
- Нет доказательства на устройстве, что все интерактивные зоны достигают 48 dp, контраст проходит AA в dynamic/light/dark schemes, а traversal order и заголовки секций оптимальны.
- Reduced motion предусмотрен, но не подтверждён системным сценарием. Infinite animation connection ring должна прекращать движение при системном запрете анимации — текущая визуальная неподвижность должна быть проверена скриншотом/semantics, а не предположена.
- Ограничение `APP_LIMIT = 200` без статуса «показаны первые 200» может скрыть приложения от пользователя и TalkBack.

### Material 3: соответствие и расхождения

| Ось M3 | Оценка | Наблюдение |
|---|---|---|
| Color / surface | Частично | Используются `ColorScheme` и surface containers, однако статусные поверхности не оформлены как единая шкала приоритетов. |
| Typography / shape | Частично | Роли MaterialTheme применяются; форма connection control осмыслена, но screen hierarchy выражена слабее, чем control. |
| Components | Частично | Material 3 компоненты есть; собственные rows нуждаются в accessibility-аудите и единых pressed/selected/error состояниях. |
| Navigation | Частично | Bottom bar/rail корректны по ширине, но information architecture не следует пользовательским задачам; wide layout не использует панели. |
| Motion | Частично | Есть reduced-motion путь и animation tokens; отсутствует описанная choreography переходов между состояниями и экранными потоками. |
| Adaptive | Fail | Изменяется только navigation chrome; нет list-detail/supporting pane, ограничения ширины контента, fold posture стратегии. |
| Accessibility | Частично | Начальная семантика есть, но нет device/screenshot/semantics acceptance evidence. |

## 2. Product UX review: VPN-клиент

Главный вывод: **новый пользователь сможет подключиться только при качественной подсказке в первом запуске; самостоятельно разобраться с источником, выбором сервера и recovery после ошибки сейчас будет не всегда.** Базовая модель уже правильная, но путь должен быть единым и контекстным.

| Сценарий | Что есть сейчас | Риск для пользователя | Требование к новому UX |
|---|---|---|---|
| Первый запуск | Welcome, legal, ручная ссылка/вставка/файл, «Позже» | После «Позже» теряется ощущение незавершённой задачи | Один setup-поток: «добавьте подписку» → проверяем импорт → «выберите сервер/Авто» → «подключение готово». Legal оставить обязательным, но не делать главным содержанием. |
| Добавление подписки | Form на onboarding и Sources; ошибки через notice | Два разных entry point и мало контекста результата | Один import sheet/flow, единое поле + Paste/File, результат: N серверов, имя источника, проблема/следующий шаг. |
| Выбор сервера | Вкладка Servers, Auto, поиск, группы по источнику | Непонятно, повлиял ли выбор на соединение | «Маршрут»/Servers в контексте Home; выбранный элемент, Auto с фактическим сервером, явный reconnect feedback. |
| Подключение | Большой control и текст состояния | Хорошо виден action, но до него скрыты prerequisites | Один primary action. Если нет prerequisites — control ведёт в соответствующий setup-flow с причиной. |
| Потеря сети | `Reconnecting`, secondary Cancel | Пользователь может принять это за первоначальное подключение | Отдельное состояние: «Сеть изменилась — восстанавливаем подключение», выбранный сервер, доступная отмена; при отсутствии сети — «Нет интернета» и Retry после возвращения сети. |
| Ошибка подключения | `Stopped(Trouble)` и retry/choose/refresh | Причина и recovery разбиты, источник сбоя не всегда очевиден | Error state: человекочитаемая причина, контекст (сервер или подписка), один primary recovery action, Diagnostics как tertiary link. |
| Смена сервера | Выбор строки, snackbar | Нет воспринимаемой транзакции | При active connection: selection → «Подключаемся к …» → connected/error; без ручного disconnect. |
| Управление приложениями | Режим, затем список и поиск | Направление исключений когнитивно тяжело | Сначала human rule («Защищать все приложения» / «Только выбранные» / «Исключить выбранные»), затем список, summary selected count, apply/reconnect copy. |
| Настройки | Базовые, advanced, diagnostics | Реальные настройки смешаны с редкими и служебными | Перегруппировать по задачам: «Подключение», «DNS», «Маршрутизация», «Приложения», «Интерфейс», «Диагностика». Только параметры с подтверждённым backend effect. |

## 3. Новая информационная архитектура

### Пользовательские сущности

1. **Подключение** — текущее состояние VPN и главное действие.
2. **Маршрут** — выбранный сервер или «Авто», его фактический выбор и источники доступных серверов.
3. **Подписка** — источник серверов: имя, актуальность, квота, состояние обновления. Это не runtime-config и не «outbound».
4. **Правила приложений** — какой трафик направляется через VPN и какой исключается.
5. **Настройки подключения** — только реально работающие и понятные последствия.

### Предлагаемая структура

Три destination сохраняют низкую нагрузку навигации, но меняют смысл:

| Destination | Содержимое | Основная роль |
|---|---|---|
| **Подключение** | Home, selected route, compact traffic, recovery states | Ежедневное подключение |
| **Серверы** | Серверы, поиск, Auto, subscriptions как управляющий источник списка | Выбрать, откуда и через что подключаться |
| **Настройки** | Подключение, DNS, Маршрутизация, Приложения, Блокировка рекламы, Производительность, Совместимость, Интерфейс, Диагностика | Менять устойчивые предпочтения и открыть инструменты поддержки |

На compact экран «Серверы» — список серверов с header «Подписки». Добавление/обновление подписки открывает modal flow, а не отдельный destination. На medium/expanded — list-detail: слева серверы/источники, справа выбранный сервер или детали подписки; Home получает supporting pane с состоянием/маршрутом без дублирования control.

DNS resolver, MTU, TLS fragmentation, Proxy и его порт — строки соответствующих смысловых групп, а не отдельного раздела «Для продвинутых». Каждая получает конкретное объяснение эффекта и ограничения. Log level, экспорт и технические поля остаются в группе «Диагностика».

**Не создавать UI:** для `READY`, `STARTING`, transport, lanes, generation, outbound, snapshot. Они остаются только в Diagnostics. Не создавать настройки, у которых нет подтверждённого backend effect; появление модели/поля недостаточно.

## 4. Home redesign

### Главный action

На Home есть ровно один primary action: **Подключиться / Отключиться**. Он остаётся на одном месте и меняет семантику по состоянию. Если prerequisite не выполнен, action запускает конкретный flow («Добавить подписку» или «Выбрать сервер»), а не выглядит как неактивная кнопка.

Вторичный постоянный элемент — clickable route summary: «Авто · [фактический сервер]» или выбранный сервер. Это единственный путь к смене сервера из Home. Трафик показывается только в connected состоянии и вторичным уровнем.

| Состояние | Показывать | Primary action | Скрыть |
|---|---|---|---|
| Disconnected | «Не подключено», выбранный маршрут, краткая готовность подписки | Подключиться; если нет prerequisites — соответствующий setup CTA | Трафик, технические статусы, прошлые ошибки без действия |
| Connecting | «Подключаемся к [серверу]», непрерывный, но ненавязчивый progress | Отменить | Переключение сервера, traffic tiles, преждевременные обещания успешного подключения |
| Connected | «Подключено», маршрут, duration, компактные up/down | Отключиться | Retry/error affordances, диагностические поля |
| Reconnecting | «Восстанавливаем подключение после изменения сети», текущий маршрут | Отменить | «Подключение» как текст — это не действие пользователя; подробная телеметрия |
| Error | Название ситуации, затронутый сервер/подписка, одно короткое объяснение | Retry / Выбрать сервер / Обновить подписку / Разрешить VPN — по причине | Код ошибки, transport, ложные «готово», одновременно несколько CTA |

Нулевые состояния не являются шестым видом Home: «Нет подписки» и «подписка без серверов» — это setup blocking states с тем же визуальным каркасом и одним действием.

## 5. Material 3 Expressive: дизайн-система

### Цвет и поверхности

Основа — system dynamic color при доступности и статическая бренд-схема как fallback. Цвет сообщает значение, а не декор: primary — активное подключение и главный action; secondary/tertiary — маршрут и нейтральная активность; error — состояние, требующее действия. Статусы не должны различаться только цветом: добавлять icon, copy и shape/motion signal. Иерархию формировать `surface`/`surfaceContainer*`, а не произвольными карточками и тенями.

### Типографика

Home использует один выразительный display/headline для состояния, title для маршрута и body для причины/последствия. Списки серверов и источников используют title + supporting text; метрики — tabular/label treatment, чтобы цифры не конкурировали со статусом. Нет технических терминов в видимой иерархии.

### Формы

Форма — семантический сигнал. Крупный connection control может морфировать между спокойной округлой idle/connected формой, мягким рабочим контуром для connecting и ясной error form. List rows, sheets и dialogs берут роли `MaterialTheme.shapes`; не вводить случайные радиусы. Выразительность сосредоточить в 1–2 важных элементах экрана, не во всех карточках.

### Motion

Motion объясняет смену состояния: control и status copy согласованно переходят Connected ↔ Connecting ↔ Error, route selection имеет короткий confirmation transition, import показывает progress/result в том же контейнере. Движение interruptible, не блокирует action, использует tokens/spring scheme, и полностью редуцируется при `ANIMATOR_DURATION_SCALE = 0`. Не анимировать счётчики и контейнеры ради украшения.

### Adaptive layout

- Compact: bottom bar, один рабочий столбец, modal sheets для импорта и действий источника.
- Medium: rail; Home с ограниченной шириной; Routes как single-pane с detail навигацией.
- Expanded/foldable book: rail + list-detail для Routes; слева список, справа сервер/подписка. Dialog/sheet превращается в side/supporting pane.
- Tabletop: status Home сверху, действия/маршрут снизу; никакая интерактивная цель не пересекает hinge.
- Ограничивать ширину text/content, не растягивать forms и кнопки на весь планшет.

### Light / dark

Проверять обе схемы с dynamic и fallback palette. Контраст: 4.5:1 для body text, 3:1 для крупного текста и UI boundary; error surface не должна становиться единственным носителем смысла. Не делать отдельный ручной contrast setting без продуктовой причины: системный контраст поддерживается platform color scheme, а собственный режим нужен только при подтверждённой потребности.

## 6. Список изменений

| Действие | Что | Причина и пользовательская проблема | Ожидаемый результат |
|---|---|---|---|
| Удалить | Отдельный пользовательский маршрут Sources как destination/detail первого класса | Подписка существует только ради списка маршрутов; отдельный экран разрывает задачу | Sources становится частью Routes, import/manage — contextual sheet/detail |
| Удалить | Технические или неработающие настройки из обычного UI | Пользователь не может предсказать эффект и теряет доверие | В настройках остаются только реальные, понятные эффекты |
| Объединить | Servers + источники подписок | Выбор сервера и происхождение списка — одна задача | Один экран Routes с сервером, Auto, подписками и состояниями обновления |
| Объединить | Error copy, причина и recovery action на Home | Сейчас сообщение и путь исправления разделены | Одна status/recovery композиция с одним CTA |
| Переработать | Onboarding | Он должен довести до готового подключения, а не просто собрать ссылку | Setup завершает импортом и ясным переходом к Home |
| Переработать | Home вокруг «подключения», не набора виджетов | Главный экран не держит user journey и статус не всегда однозначен | Один action, единая state machine, route summary, secondary traffic |
| Переработать | Apps rules | Режимы routing трудно понять из названий | Сначала человеческое правило, затем список и summary выбора |
| Переработать | Settings hierarchy | Повседневное, совместимость и служебные инструменты соседствуют | Один экран «Настройки» с группами по смыслу, честным apply/reconnect copy и отдельной группой «Диагностика», но без раздела «Для продвинутых» |
| Создать | Design-token contract для status/surface/motion/semantic labels | Выразительный control не масштабируется как единый язык | Повторяемая M3 Expressive система без «добавить Card и Button» |
| Создать | Adaptive Routes list-detail и Home supporting layout | Rail сам по себе не делает планшетный UX | Полезные панели на medium/expanded, hinge-safe layouts |
| Создать | UI acceptance suite: semantics + screenshot matrix + device flows | Доступность и состояния нельзя считать выполненными по коду | Проверяемые compact/medium/expanded, light/dark, reduced-motion сценарии |

## 7. Реализационные задачи и порядок

Ниже — порядок, который не требует переписывать backend. Перед реализацией каждой настройки подтверждать её effect существующим action/config path; иначе не показывать её.

1. **P0 — UX contract, терминология и корректность Home actions.** Зафиксировать названия «Подключение», «Серверы», «Подписки», «Правила приложений», product copy для `Connection`/`Trouble`, invariant «runtime-поля только в Diagnostics» и исправить неверные переходы `CHOOSE_SERVER`/`REFRESH_SOURCE` до любого визуального редизайна.
2. **P0 — результаты import/update и motion preference.** Ввести success, failure, empty, partial-success для подписки, не очищать ссылку заранее; подключить системный reduced motion, который сейчас не передаётся в Android capabilities.
3. **Navigation и adaptive shell.** Ввести destination «Подключение / Серверы / Настройки», сохраняемую navigation/onboarding state, width/posture policy и content-width constraints. Не добавлять новую библиотеку, если текущий Compose stack уже предоставляет требуемый adaptive API; иначе принять минимальную совместимую зависимость отдельно.
4. **Home state machine и expressive tokens.** Переработать Home по пяти состояниям, сохранить один primary action, route summary и reduced-motion behaviour; добавить семантику и testable state fixtures.
5. **Routes: серверы и подписки.** Собрать список, Auto, поиск, import/update/remove flow и reconnect confirmation в одну информационную архитектуру; на expanded — list-detail.
6. **Onboarding.** Переиспользовать import flow, вернуть пользователя в определённое состояние Home/Routes, явно показать успешный импорт и следующий шаг; встроить VPN/notification permission в объяснённый пользовательский поток.
7. **Настройки и правила приложений.** Реализовать Settings UX/backend contract из §8: один экран с группами по смыслу, без раздела «Для продвинутых»; добавить понятные rule summaries и honest reconnect/apply copy. Не выводить параметры без подтверждённого backend effect и persistence round-trip.
8. **Диагностика.** Оставить internal fields строго здесь, улучшить экспорт, доступ к нему и privacy copy; не выносить технику назад в Home.
9. **Accessibility и визуальная приёмка.** Compose semantics tests для primary flow; screenshots compact/medium/expanded × light/dark × five Home states; ручной TalkBack, 48 dp, contrast и reduced-motion прогон на устройстве/AVD.

## 8. Дополнение к плану: Settings UX / Backend contract

### Принцип

«Настройки» — один пользовательский раздел, а не витрина внутренних опций sing-box. Группы раскрывают смысл настройки, а не уровень технической подготовки пользователя. «Диагностика» остаётся инструментом поддержки, а не набором настроек.

Каждая строка Settings до появления в UI проходит три обязательных вопроса:

1. Какую проблему пользователя решает?
2. Какой конкретный backend effect вызывает?
3. Как пользователь проверит результат?

Если на любой вопрос нет подтверждаемого ответа, строка не появляется. Дополнительное условие: значение обязано сохраняться и восстанавливаться после перезапуска; одного поля в data class или генераторе конфигурации недостаточно.

### Контракт групп

| Группа | Пользовательская настройка | Backend contract и проверяемый результат | Статус для UI |
|---|---|---|---|
| Подключение | «Показывать скорость в уведомлении» | Изменяет содержимое foreground notification. Нужен выбор режима отображения (скорость / объём / оба), а не текущий общий on/off. | Backend дополнить |
| Подключение | «Режим: VPN / Proxy» | Взаимоисключающий выбор inbound/config generation; для Proxy показывать порт, доступ из LAN и предупреждение о переподключении. | После исправления persistence |
| DNS | «Использовать DNS через подключение» | Сейчас DNS через маршрут — инвариант: proxy DNS идёт через selector, DNS перехватывается. Не рисовать фиктивный toggle; показывать summary до появления отдельного direct-DNS режима. | Summary only |
| DNS | «DNS: Автоматически / Cloudflare / Quad9 / Пользовательский» | Выбор и валидация upstream resolver. Разделять DNS для подключения и direct/bootstrap resolver; пользовательский адрес должен быть проверяемым. | Custom endpoint условно доступен; presets требуют UX contract |
| DNS | «Скрывать регион клиента (EDNS Client Subnet)» | Явная передача ECS policy в generated config с описанием scope. | Backend отсутствует |
| DNS | «Использовать FakeIP» | FakeIP DNS, исключения и предупреждение совместимости; только при сохранении domain context для routing. | Backend отсутствует |
| DNS | «Использовать: Авто / IPv4 / IPv6» | Единственный policy для `dns.strategy`, видимый effective value и reconnect. Не добавлять отдельное «Предпочитать IPv4»: это дубликат. | Backend дополнить: сейчас жёстко `ipv4_only` |
| Маршрутизация | «Весь трафик через VPN / Умная маршрутизация / Пользовательские правила» | Разные generated route sections. Не заменять этим существующие независимые эффекты LAN/STUN/strict route. | Backend contract отсутствует |
| Маршрутизация | «Доступ к локальным устройствам» | Включает/исключает bypass LAN rules; объясняет, что доступ к устройствам в локальной сети изменится после переподключения. | Доступно после исправления persistence |
| Маршрутизация | «Правила» — напрямую / через VPN / блокировать | Создание, валидация, порядок и generation rule-set. Каждое правило должно быть объяснимо и иметь preview результата. | Backend contract отсутствует |
| Приложения | «Все через VPN / Только выбранные / Выбранные вне VPN» и список приложений | Один mode + package list, генерирующие `include_package` / `exclude_package`; summary выбранных и reconnect effect. | После исправления persistence |
| Блокировка рекламы | «Блокировка рекламы» | Подключает только уже скачанный adblock rule-set; показывает количество правил, дату обновления, download/error state. | После исправления persistence; загрузка уже есть |
| Производительность | TCP Fast Open / Multipath TCP | Socket options в outbounds; предупреждение об экспериментальном характере и reconnect. | UI/action/persistence отсутствуют |
| Производительность | «Размер пакета MTU: Авто / число» | TUN configuration; custom значение в допустимом диапазоне и понятный reset к Auto. | Custom частично доступен; Auto contract отсутствует |
| Совместимость | «TLS Fragmentation: Авто / Вкл / Выкл» | Policy для TLS-capable outbounds и reconnect. «Вкл» нельзя сопоставить существующим `record`/`fragment` без продуктового решения; Auto отсутствует. | Backend/UI contract дополнить |
| Интерфейс | Тема / язык | Немедленный визуальный эффект; язык — только на поддерживаемых Android версиях. | После исправления persistence |
| Диагностика | Runtime status, журналы, экспорт, core, активный сервер, DNS и правила | Read-only support tools. В обычных группах не показывать generation, lanes, transport, outbound, snapshot. | Доступно |

### Что явно не является настройкой

- восстановление сети, connection timeout, runtime retry и обработка смены сети — автоматическая логика подключения;
- runtime state и любая телеметрия, не помогающая изменить пользовательский выбор;
- отдельное «Предпочитать IPv4», поскольку оно дублирует DNS strategy;
- отдельные режимы Proxy, порт и LAN-доступ: это один режим и его зависимые параметры, не три независимые настройки.

### Обязательный подготовительный этап

До UI-редизайна Settings закрыть persistence round-trip: текущий `SettingsCodec.decode/encode` не сохраняет часть уже объявленных полей, включая режим приложений, AdBlock, VPN/Proxy inbounds, theme/language, TFO и Multipath. Пока это не исправлено, переключатели создадут ложное впечатление, что выбор действует после перезапуска.

### Порядок исполнения Settings

1. Добавить тесты round-trip для каждого поля `Settings` и восстановить persistence существующих backend-connected параметров.
2. Перестроить один экран Settings по группам: Подключение, DNS, Маршрутизация, Приложения, Блокировка рекламы, Производительность, Совместимость, Интерфейс, Диагностика.
3. Включить только строки с работающим action → storage → config/runtime path; у каждой показать краткое последствие и, где нужно, «Применится после переподключения».
4. Для ECS, FakeIP, DNS strategy, smart/custom routing rules, Auto MTU и Auto TLS сначала согласовать и реализовать backend contract с проверкой generated config; затем проектировать UI.
5. Протестировать flow: изменение → visual acknowledgement → reconnect (если нужен) → проверяемый эффект; отдельно TalkBack, large text и состояния unavailable/downloading/error.

## Непринимаемые решения

- Перенос Flutter-экранов HB1 или их структуры один-в-один.
- UI, построенный вокруг runtime models, внутренних фаз и диагностических названий.
- Новые переключатели «на будущее» или для полей, которые backend фактически не применяет.
- Украшение M3 Expressive бесконечными анимациями и произвольными карточками вместо ясной иерархии состояния и действия.
